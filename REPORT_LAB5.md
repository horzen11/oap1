# Лабораторна робота №5
## Уразливості і захист

**Тема:** Виявлення та виправлення типових уразливостей вебзастосунку.

**Проєкт:** Реєстр заявок на обладнання.

**Посилання на репозиторій:** https://github.com/soshevchik/Shevtsova.git

---

## Мета роботи

Метою роботи є навчитися знаходити типові уразливості вебзастосунків у навчальному середовищі, відтворювати їх локально, виправляти на рівні коду та конфігурації, а також перевіряти результат за принципом: проблема → відтворення → виправлення → перевірка.

---

## Реалізовані сценарії

У лабораторній роботі реалізовано всі 4 сценарії, необхідні для рівня «відмінно»:

1. SQL Injection.
2. XSS.
3. Broken Access Control / IDOR.
4. Security Misconfiguration.

---

## Сценарій A — SQL Injection

### Було

У студентських проєктах SQL Injection виникає тоді, коли дані користувача вставляються в SQL-запит через конкатенацію рядків. У такому випадку введений текст може змінити логіку SQL-запиту.

Потенційно небезпечний підхід:

```ts
WHERE r.comment LIKE '%${search}%'
```

### Відтворення

Для перевірки використовується пошук із проблемним введенням, наприклад рядок зі спеціальними символами. У вразливій версії такий рядок міг би змінити логіку SQL або викликати помилку SQL.

### Виправлення

У репозиторії запити до SQLite для пошуку та доступу до заявок замінені на параметризовані запити. Дані передаються окремо від SQL-коду.

Приклад захищеного запиту:

```ts
WHERE r.ownerUserId = ?
  AND (r.itemCode LIKE ? OR r.comment LIKE ? OR u.fullName LIKE ?)
```

Параметри передаються окремим масивом:

```ts
[ownerUserId, like, like, like]
```

### Перевірка

Після виправлення введення зі спеціальними символами не змінює структуру SQL-запиту. Пошук працює коректно, а сервер не повертає аварійну помилку.

## Сценарій Б — XSS

### Було

XSS виникає тоді, коли дані користувача вставляються на сторінку як HTML. Наприклад, якщо коментар користувача вставити через `innerHTML`, браузер може сприйняти його як розмітку.

### Відтворення

У поле коментаря можна ввести HTML-подібний текст. У небезпечному рендері такий текст міг би змінити структуру сторінки.

### Виправлення

На frontend дані користувача виводяться через DOM API та `textContent`. Це означає, що введений текст відображається саме як текст, а не як HTML.

Приклад:

```ts
const td = document.createElement("td");
td.textContent = text;
row.appendChild(td);
```

### Перевірка

Після виправлення HTML/JS-подібне введення не виконується і не змінює DOM. Воно відображається як звичайний текст у таблиці.

## Сценарій В — Broken Access Control / IDOR

### Було

IDOR виникає тоді, коли користувач може отримати доступ до чужого ресурсу, просто підставивши інший `id` у URL. Якщо перевіряти тільки `id` заявки, але не перевіряти власника, користувач може прочитати, змінити або видалити чужий запис.

### Відтворення

Для перевірки використовується заголовок:

```http
X-Demo-UserId: demo-user-1
```

Якщо спробувати звернутися до заявки, що належить іншому користувачу, сервер має відмовити в доступі.

### Виправлення

У проєкті додано:

- поле `ownerUserId` у таблицю `Requests`;
- middleware `demoAuth`, який читає `X-Demo-UserId`;
- перевірку власника ресурсу на backend;
- захист операцій читання, редагування та видалення.

Захищений запит:

```ts
WHERE r.id = ? AND r.ownerUserId = ?
```

### Перевірка

- Якщо немає заголовка `X-Demo-UserId`, сервер повертає `401 Unauthorized`.
- Якщо користувач відкриває чужу заявку, сервер повертає `404 Not Found`.
- Якщо користувач відкриває свою заявку, запит працює успішно.

## Сценарій Г — Security Misconfiguration

### Було

Security Misconfiguration може проявлятися у надто широкому CORS, відсутності базових security headers або показі зайвих технічних деталей у відповідях.

### Виправлення

У backend додано базові захисні HTTP-заголовки:

```ts
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
```

CORS налаштовано не через `*`, а через список дозволених origin:

```ts
http://localhost:5173
http://127.0.0.1:5173
http://localhost:5500
http://127.0.0.1:5500
```

Також додано дозволений заголовок:

```http
X-Demo-UserId
```

### Перевірка

Заголовки можна перевірити через DevTools → Network або через PowerShell:

```powershell
Invoke-WebRequest -Uri "http://localhost:3000/health" -UseBasicParsing
```

У відповіді присутні security headers. Помилки повертаються в єдиному JSON-форматі.

## Приклади перевірки

### Перевірка 401 без заголовка

```powershell
Invoke-WebRequest -Uri "http://localhost:3000/api/v1/requests" -UseBasicParsing
```

Очікувано: `401 Unauthorized`.

### Перевірка успішного запиту з demo-user

```powershell
Invoke-WebRequest -Uri "http://localhost:3000/api/v1/requests" -Headers @{"X-Demo-UserId"="demo-user-1"} -UseBasicParsing
```

Очікувано: `200 OK`.

### Перевірка SQLi-safe пошуку

```powershell
Invoke-WebRequest -Uri "http://localhost:3000/api/v1/requests/search-safe?q=' OR 1=1 --" -Headers @{"X-Demo-UserId"="demo-user-1"} -UseBasicParsing
```

Очікувано: запит не ламає SQL і не повертає чужі дані.

### Перевірка IDOR

1. Отримати список заявок для `demo-user-1`.
2. Спробувати звернутися до заявки іншого користувача з тим самим заголовком.
3. Очікувано: `404 Not Found`.

## Таблиця ризиків

| Ризик | Наслідок | Виправлення |
|---|---|---|
| SQL Injection | Зміна логіки SQL-запиту або витік даних | Параметризовані SQL-запити |
| XSS | Виконання небезпечного HTML/JS у браузері | `textContent` замість небезпечного HTML-рендеру |
| IDOR | Доступ до чужих заявок | `ownerUserId` + перевірка власника на backend |
| Misconfiguration | Зайві технічні дані або слабка конфігурація | Security headers, CORS whitelist, єдиний формат помилок |

## Висновок

У результаті виконання лабораторної роботи було додано базові механізми безпечної розробки до вебзастосунку. Було реалізовано захист від SQL Injection, XSS, IDOR та помилок конфігурації. Також було налаштовано демо-ідентифікацію через `X-Demo-UserId`, перевірку доступу до ресурсів, параметризовані SQL-запити, безпечний рендеринг даних на frontend і базові security headers.
